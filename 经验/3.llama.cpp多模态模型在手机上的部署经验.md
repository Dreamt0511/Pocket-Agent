llama.cpp 多模态模型在 Android Termux 上的部署与调试

适用场景

在 Android 手机（Termux 环境）上使用 llama.cpp 运行多模态视觉语言模型（如 GELab-Zero-4B），进行图像理解和 GUI 自动化操控。模型需要 Vulkan GPU 加速但遇到驱动兼容性问题。

---

核心问题与解决方案脉络

整个调试过程的核心矛盾是：模型图像编码阶段强行调用 Vulkan GPU 导致驱动崩溃，纯 CPU 又因内存不足被系统 OOM Killer 查杀。最终通过分隔图像编码与文本推理的后端、限制图像 token 数量、调整上下文窗口大小三者配合，找到稳定运行点。

基本运行环境：

· 设备：小米 17 Pro (Adreno 840 GPU)，Android Termux
· 模型：GELab-Zero-4B-preview (Q4_K_M 量化，2.39 GiB)
· llama.cpp 备份版本（约 2025-05 构建）

---

关键参数说明

参数 作用 用法建议
-ngl N 卸载 N 层到 GPU Android Vulkan 驱动不稳时设 0 保底，稳定后设 40 加速推理
--no-mmproj-offload 图像编码器不走 GPU 必加，绕过 Adreno Vulkan 驱动 bug 的核心
--image-max-tokens N 限制图像编码 token 数 64=极低内存/低精度，128=甜点值，256+=高精度/高内存
-c N 上下文窗口大小 KV cache 内存随 N 线性增长；20000 对应约 2.8 GB
--no-warmup 跳过空推理预热 减少启动时间和内存峰值
--temp 采样温度 0.7 通用，GUI 场景可稍低（0.3-0.5）
-t N CPU 线程数 8 线程适配高端手机，内存紧张时可减至 4
-ctk q8_0 / -ctv q8_0 KV cache 量化 用 q8_0 可降低内存占用但影响精度，内存足够时用默认 f16

调试步骤详解

步骤 1：定位问题（初始失败）

现象：运行 llama-mtmd-cli 后崩溃，提示 vk::DeviceLostError

```
libc++abi: terminating due to uncaught exception of type vk::DeviceLostError
Aborted
```

原因：图像编码阶段强制使用 Vulkan GPU，Adreno 840 驱动在处理 CLIP 视觉编码器时不稳定。

尝试的失败方案：

· -ngl 0 完全禁用 GPU → 仍然崩溃（--no-mmproj-offload 默认启用，图像编码仍走 Vulkan）
· -ngl 20 部分卸载 → 同上崩溃
· 环境变量 GGML_VULKAN=0 → 备份版二进制内置 Vulkan 支持，环境变量不生效
· 重新编译禁用 Vulkan → 用户明确需要 GPU 加速，否定了此方案

关键发现：崩溃发生在 encoding image slice... 阶段，后续的 warmup 和模型加载均成功——问题仅在于图像编码的后端选择。

步骤 2：首次突破（64 token 成功）

发现：查看 llama-mtmd-cli --help，找到 --no-mmproj-offload 和 --image-max-tokens 两个关键参数。

--no-mmproj-offload 的作用是：将 CLIP 图像编码器强制锁定在 CPU 后端，而主模型推理仍可使用 Vulkan。这样既避开了驱动 bug，又保留了 GPU 加速。

首次成功命令：

```bash
./build/bin/llama-mtmd-cli \
  -m "/storage/emulated/0/本地模型/GELab-Zero-4B-preview-q4_k_m.gguf" \
  --mmproj "/storage/emulated/0/本地模型/GELab-Zero-4B-preview-f16.mmproj" \
  --image "test_picture.png" \
  -p "请描述这张图片的内容" \
  -n 256 \
  -ngl 40 \
  -t 8 \
  --temp 0.7 \
  -c 4096 \
  --no-mmproj-offload \
  --image-max-tokens 64
```

结果：

· 模型推理 37/37 层在 Vulkan GPU（高效）
· 图像编码在 CPU（内存 9.14 MiB，耗时 2.1 秒）
· KV cache 仅 576 MiB
· 首次完整输出了图像描述

代价：64 token 时图像极度压缩，猫被误认为企鹅，精度很低。

步骤 3：盲目加资源导致 OOM（内存超限）

现象：将 -c 设为 20000（上下文窗口扩大），模型加载后系统直接 Killed。

原因：KV cache 内存与上下文大小成正比：

· -c 4096 → KV cache 576 MiB
· -c 8192 → KV cache 1152 MiB
· -c 20000 → KV cache 2844 MiB

加上模型本体 (2053 MiB) 和 CPU compute buffer，总显存超过 5 GiB，加上系统占用触发了 Android OOM Killer。

解决方案：降低上下文窗口或保持 --image-max-tokens 极低（64）时上下文可安全扩展到 20000；提高图像精度时必须相应缩减上下文，或依赖设备总内存余量。

步骤 4：验证大上下文 + 低图像精度（-c 8192 成功）

逐步验证：

· -c 8192 --image-max-tokens 64 → 成功，KV cache 1152 MiB，识别错误（企鹅）
· -c 20000 --image-max-tokens 64 → 理论上可行但未测试

步骤 5：提升图像精度 + 大上下文（-c 20000 --image-max-tokens 256 成功）

现象：运行以下命令时用户感觉"卡住"，实际是图像编码时间较长。

```bash
-c 20000 --image-max-tokens 1024
```

实际结果：命令成功执行，耗时 36.5 秒，猫被正确识别，总内存约 5 GiB 未触发 OOM。

步骤 6：优化响应速度（寻找甜点值）

通过递减测试找到图像质量与速度的平衡：

--image-max-tokens CPU 内存 编码时间 识别精度
64 9 MiB 2.1s 低（猫变企鹅）
128 18 MiB 5.3s 良好（猫、墨镜、屏幕选项）
256 ~36 MiB ~9s（推算） 高
1024 322 MiB 18.3s 很高

推荐甜点值：

· 日常使用 / GUI 操控：--image-max-tokens 128，速度与精度平衡
· 需要详细文字识别：--image-max-tokens 256，可清晰识别按钮文字
· 极致精度：--image-max-tokens 1024，但需接受较长等待和内存压力

常见问题排查

症状 原因 解决方案
vk::DeviceLostError 崩溃 图像编码走 Vulkan 导致驱动锁死 加 --no-mmproj-offload
进程被 Killed 总内存超限（KV cache + 模型 + 图像缓冲区） 降低 -c 或 --image-max-tokens
encoding image slice... 后无输出 正常等待（CPU 编码图像需 5-35 秒） 等待；可加 --verbose 看详细进度
无效参数 --image-max-pixels 参数名错误 改用 --image-max-tokens
模型文件 No such file or directory 路径错误或文件名拼写错误（f16.gguf 实际是 q4_k_m.gguf） ls 确认实际文件名后再填写
llama-cli: No such file or directory 未编译，或 build/bin 为空 编译项目；或从备份复制二进制文件，确认当前目录是 ~/llama.cpp

环境备份与恢复

编译好的 build/bin/ 目录应妥善备份（用户已备份至 /storage/emulated/0/本地模型/llama-backup/bin/）。恢复时：

```bash
mkdir -p ~/llama.cpp/build/bin
cp -r /storage/emulated/0/本地模型/llama-backup/bin/* ~/llama.cpp/build/bin/
chmod +x ~/llama.cpp/build/bin/*
```

后续优化方向

1. KV cache 量化：使用 -ctk q8_0 -ctv q8_0 可将 KV cache 内存减半，允许更大上下文
2. 官方 GELab-Zero 套件：文章提到的完整工程套件（stepfun-ai/gelab-zero）自动化处理设备适配，建议后续迁移
3. 流式输出：结合 ADB 截屏与 llama-server 实现实时 GUI Agent
4. 多图批处理：利用 --image 支持逗号分隔的多文件，一次推理多张截图
5. 编译优化：若需更新 llama.cpp，编译时明确 -DGGML_VULKAN=ON 并针对 Adreno 优化调度参数
