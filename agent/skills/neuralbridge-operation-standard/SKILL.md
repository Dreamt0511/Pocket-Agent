# NeuralBridge MCP 操作标准规范

## 🎯 适用场景（只有这些场景才使用本技能）
✅ 所有需要UI交互的操作：点击、滑动、输入、查找UI元素、截图分析、页面验证等
❌ 能用phone-control-guide完成的操作不要用本技能，避免浪费token

> ⚠️ **使用前提**：在执行手机操控任务前，**必须先查阅 `phone-control-guide` skill**，优先使用 Android 原生 Shell 命令或 Termux API 命令。确认零 token 方式无法实现后，再使用以下 NeuralBridge 工具。
> ⚡ **本规范包含完整的性能优化指南和故障排查流程**，请完整阅读所有章节，按照规范操作可以解决99%的操控延迟、操作失败问题。
## 核心三原则（强制执行）
1. **坐标绝对禁止猜测**：所有点击/长按/滑动的坐标必须 100% 来自 `android_get_ui_tree` 的返回结果，禁止通过截图视觉识别、估算坐标
2. **每步必验证**：任何操作执行后必须通过截图或 UI 树查询验证操作结果，确认成功后再进行下一步
3. **专用工具优先**：优先使用对应场景的专用工具，禁止用通用点击/滑动模拟：
   - 启动应用用 `android_launch_app`，禁止点击桌面图标
   - 系统操作用 `android_global_action`，禁止点击导航栏按钮
   - 查找元素用 `android_find_elements`/`android_get_ui_tree`，禁止视觉识别
   - 按键操作优先用 `android_press_key`，禁止模拟坐标点击导航栏按钮
4. **全程自动执行**：所有操作必须完整自动执行，禁止中途停止让用户手动操作，只有当所有技术方案都尝试失败后，才能告知用户无法完成

## 一、元素定位标准（怎么找坐标）
### 1. 定位流程
```mermaid
graph LR
A[需要操作某个元素] --> B[调用 android_get_ui_tree 获取全量 UI 结构]
B --> C[通过 text/resource_id/desc 匹配目标元素]
C --> D[提取元素 bounds 字段: [left, top, right, bottom]]
D --> E[计算精确中心点: x=(left+right)/2, y=(top+bottom)/2]
E --> F[使用计算得到的坐标执行操作]
```

### 2. bounds 解析规则
- UI 树返回的 bounds 格式为 `[left, top, right, bottom]`，分别代表元素的四个边界坐标
- 中心点计算必须严格按照公式：
  ```python
  x = (left + right) // 2
  y = (top + bottom) // 2
  ```
- 禁止对坐标进行任何"大概"、"差不多"的调整

### 3. 元素匹配优先级
1. 优先用 `resource_id` 匹配（稳定性最高，不会随语言/主题变化）
2. 其次用 `text` 匹配（可见文字，准确性高）
3. 最后用 `content_desc` 匹配（无障碍描述）
4. 禁止用位置顺序匹配（比如"第三个按钮"）

## 二、操作确认标准（怎么确认点对了）
### 1. 点击前确认
执行操作前必须确认：
- 匹配到的元素 `text/resource_id` 和目标完全一致
- 元素的 `bounds` 在屏幕可见范围内（y 坐标在 0~屏幕高度之间）
- 元素具有可交互属性（`flags` 包含 `c`=可点击、`f`=可聚焦等）

### 2. 典型场景确认要点
| 操作类型 | 确认内容 |
|---------|---------|
| 点击按钮 | 确认按钮 text 是目标文字，且 bounds 符合预期 |
| 打开应用 | 确认包名正确，优先用 `android_launch_app` |
| 输入文本 | 1. 确认输入框已获得焦点（光标出现）<br>2. 检查输入框是否有旧内容，有则先清空 |
| 长按操作 | 确认长按位置在元素范围内，且时长不会触发系统手势 |

## 三、结果验证标准（怎么确认操作成功）
### 1. 验证方式（二选一即可，优先用 UI 树）
#### 方式1：UI 树验证（最快最准确）
操作后重新调用 `android_get_ui_tree`，确认：
- 目标元素状态变化（比如按钮消失、文本变化、新元素出现）
- 页面 package_name 符合预期（比如启动应用后 package_name 变为目标应用）

#### 方式2：截图验证（直观）
操作后调用 `android_screenshot`，肉眼确认：
- 操作效果符合预期（比如应用打开、页面跳转、菜单弹出）
- 没有出现误操作（比如返回桌面、打开错误应用）

### 2. 验证失败处理
如果验证不通过：
1. 立即停止后续操作
2. 重新获取 UI 树定位元素
3. 分析失败原因（坐标错误、元素消失、系统拦截等）
4. 调整后重试，禁止连续盲目点击

## 四、典型操作完整流程示例
### 示例：打开笔记应用并点击新建按钮
```
1. 【定位】调用 android_get_ui_tree 获取桌面 UI 结构
2. 【匹配】找到 text="笔记" 的应用图标元素，bounds=[931,2116,1111,2296]
3. 【计算】中心点 x=(931+1111)/2=1021, y=(2116+2296)/2=2206
4. 【操作】调用 android_tap(x=1021, y=2206)
5. 【验证】调用 android_get_ui_tree，确认 package_name 变为 com.miui.notes
6. 【定位】在新 UI 树中找到 resource_id="note_add" 的新建按钮，bounds=[931,2116,1111,2296]
7. 【计算】中心点 x=1021, y=2206
8. 【操作】调用 android_tap(x=1021, y=2206)
9. 【验证】调用 android_screenshot，确认进入新建笔记界面
```

## 五、禁止行为（违者直接视为操作失败）
❌ 禁止在没有 UI 树依据的情况下猜测坐标
❌ 禁止通过截图视觉识别坐标后点击
❌ 禁止操作后不验证直接进行下一步
❌ 禁止用点击桌面图标的方式打开应用，必须用 `android_launch_app`
❌ 禁止在自定义 WebView 页面使用 `android_input_text`（先确认输入框是标准 EditText）
❌ 禁止长按超过 500ms，避免触发系统全局手势
❌ 禁止中途停止操作让用户手动完成，必须全程自动执行直到成功或所有方案失败

## 六、常见问题解决方案
### 0. 系统弹窗/权限申请处理（优先处理）
**操作前必须先检查是否有弹窗遮挡**，如有弹窗优先处理：
- 🔘 **权限申请弹窗**（"允许/拒绝"类）：
  - 非敏感权限（通知、存储等）：优先点击"允许"
  - 敏感权限（相机、麦克风、位置等）：先询问用户确认后再操作
  - 找不到"允许/拒绝"按钮：点击弹窗外部区域尝试关闭
- 📢 **广告弹窗/更新提示**：
  - 优先找"关闭"、"跳过"、"×"按钮点击
  - 没有关闭按钮：按back键返回关闭
- ⚠️ **其他弹窗**（警告、提示类）：
  - 有"确认"、"知道了"按钮就点击
  - 没有就按back键尝试关闭
- **处理原则**：弹窗不处理会挡住后续所有操作，必须先处理完弹窗再继续执行任务

### 1. 元素找不到
- 先检查是否有弹窗遮挡
- 检查是否在正确的页面
- 尝试滚动页面后重新获取 UI 树
- 用 `android_find_elements` 按条件搜索

### 2. 点击无反应
- 确认元素 `flags` 包含可点击属性
- 确认坐标计算正确
- 尝试点击元素其他位置（比如左上角，不要只点中心点）

### 3. 输入失败
- 确认输入框已获得焦点
- **输入前必须检查**：确认输入框没有旧内容，有则先清空
  - 清空方法1：全选（长按→全选）→ 按删除键
  - 清空方法2：连续按删除键20次（简单可靠）
  - 清空方法3：直接输入新内容覆盖（适用于搜索场景）
- 确认输入框是标准 Android EditText，不是自定义 WebView
- 降级为剪贴板粘贴方案：`set_clipboard` → 长按 → 点击粘贴
- **非标准输入框（如拼多多搜索框、自定义渲染输入框）适配方案**：
  1. 这类输入框无法通过resource_id匹配，也不支持直接识别为EditText元素，无需等待焦点提示，直接点击输入框可见区域中心即可激活
  2. 即使调用`android_input_text`返回"元素找不到"错误，实际部分应用仍会接收输入，可直接点击搜索/提交按钮尝试
  3. 若仍失败，先将目标文本复制到剪贴板，长按输入框区域1000ms，无需找到粘贴按钮，直接点击搜索按钮，主流电商/社交应用会自动识别剪贴板内容执行搜索
  4. 清空原有内容方案：如果长按找不到全选按钮，连续按delete键清空，或直接输入新内容覆盖，无需完全清空即可触发搜索
- **自定义WebView输入框（如DeepSeek/ChatGPT/Claude等AI应用通用）适配方案**：
  1. **识别信号（满足任意一个即可触发）**：
     - 调用 `android_input_text` 返回 `Could not get node reference for element` 错误
     - UI树中找不到标准`EditText`类型元素
     - 应用包名属于跨端应用：`com.deepseek.chat`、`com.openai.chatgpt`、`com.anthropic.claude`、`com.microsoft.copilot`等
  2. **强制执行流程（必须按顺序执行，优先使用系统快捷功能，全程自动完成）**：
     1. 点击输入框可见区域中心激活（优先点击占位文本所在位置，如"输入问题..."）
     2. 调用 `android_set_clipboard(content="目标文本")` 将需要输入的内容存入系统剪贴板
     3. 等待1秒（系统会弹出剪切板粘贴提示），重新获取UI树，优先查找包含"粘贴"文本的悬浮提示按钮并点击（无需长按）
     4. 若没有找到悬浮粘贴提示，再调用 `android_long_press(x=输入框x坐标, y=输入框y坐标, duration=1200)` 长按输入框区域
     5. 重新获取UI树，查找包含"粘贴"文本的按钮并点击
     6. 若找不到"粘贴"按钮，点击长按点上方约100px位置触发系统粘贴
     7. 验证内容已输入后，点击发送按钮
     8. 所有步骤必须自动执行完成，禁止中途停止让用户手动粘贴
  3. **禁止行为**：
     - 禁止反复调用`android_input_text`，失败1次就必须切换到此方案
     - 禁止直接调用系统`input`命令（Termux环境无执行权限，会触发空指针异常）

## 七、性能优化指南（解决反应慢/延迟高）
### 核心性能数据（本地实测）
- 简单操作（点击/返回/启动应用）：30-80ms
- UI树获取：150-250ms
- 截图（缩略图）：100-150ms
- 👉 MCP本身性能极高，延迟主要来自调用方式和流程

### 优化原则（强制执行）
1. **减少调用次数**：能用一个接口完成的不要拆成多个
   - ✅ 优先用 `android_get_screen_context` 代替分开调用 `android_get_ui_tree` + `android_screenshot`，减少一次调用，性能提升40%
   - ✅ 优先用 `android_scroll_to_element` 代替自己循环滑动+查找
   - ✅ 优先用 `android_wait_for_element` 代替自己轮询查找

2. **高效接口选择**：
   | 场景 | 优先选择 | 避免使用 |
   |------|---------|---------|
   | 查找特定元素 | `android_find_elements` | `android_get_ui_tree` + 自己过滤 |
   | 获取页面+截图 | `android_get_screen_context` | 分开调用两个接口 |
   | 滚动找元素 | `android_scroll_to_element` | 循环调用 `android_swipe` |
   | 等待元素出现 | `android_wait_for_element` | 循环调用 `android_find_elements` |

3. **参数优化**：
   - UI树默认用 `filter="interactive"`，只获取可交互元素，速度提升30%
   - 截图默认用 `quality="thumbnail", max_width=360`，不需要分析图片时不要用全尺寸
   - 不需要全量元素时不要开 `include_all_elements`

4. **缓存复用**：
   - 页面没有变化时，缓存UI树结果，不要每次操作都重新获取
   - 同一页面的多步操作，一次性获取所有需要的坐标后批量执行

### 优化效果
按照以上原则调整，操控速度可提升30%-200%，彻底解决延迟高的问题。

## 八、故障排查与重试指南（禁止半途而废）
### 🔴 核心原则（强制执行）
**遇到任何操控失败，绝对禁止直接返回失败。必须尝试至少2-3种不同方案，**最多重试3次**，确认所有可行路径都失败后，才能最终告知用户无法完成。禁止无限重试浪费资源。
**绝对禁止中途停止让用户手动操作**，所有操作必须全程自动执行，除非用户明确要求手动干预。

### 通用排查流程
```
1. 操作失败 → 分析错误原因
2. 重试1-2次，确认不是偶发问题
3. 尝试第1种备选方案 → 成功则继续
4. 失败则尝试第2种备选方案 → 成功则继续
5. 失败则尝试第3种备选方案 → 成功则继续
6. 所有方案都失败 → 告知用户并说明尝试过的所有方法
```

### 常见问题的备选方案
#### 1. 点击/滑动/输入无反应
- 方案1：重新获取UI树，确认元素定位正确，检查是否有可点击属性
- 方案2：调整点击位置，尝试元素的四个角而不是中心点
- 方案3：换定位方式（resource_id→text→content_desc→直接坐标）
- 方案4：调整操作参数（长按代替点击，调整滑动速度）

#### 2. 找不到元素
- 方案1：确认页面正确，没有弹窗遮挡，尝试滚动页面
- 方案2：调整搜索参数，去掉严格匹配条件，用部分匹配
- 方案3：使用 `android_scroll_to_element` 自动滚动查找
- 方案4：用 `android_wait_for_element` 等待3-5秒加载

#### 3. 输入失败
- 方案1：确认输入框已获得焦点，重新点击激活后重试`android_input_text`
- 方案2：**优先使用剪贴板粘贴方案**：
  1. 将内容复制到剪贴板
  2. 等待1秒优先点击系统弹出的悬浮"粘贴"提示按钮（无需长按）
  3. 无悬浮提示时再长按输入框触发粘贴
- 方案3：降级为模拟键盘输入：使用`android_press_key`逐个输入字符（仅用于短文本）

#### 4. 启动应用失败
- 方案1：确认包名正确，用 `android_list_apps` 验证
- 方案2：用Shell命令 `am start -p 包名` 启动（phone-control-guide）
- 方案3：回到桌面，找到应用图标点击启动

### 失败返回要求
只有所有方案都尝试过仍失败时，才能返回失败，且必须说明：
1. 你尝试了哪些方法（至少3种）
2. 每种方法的错误信息
3. 可能的原因和建议的排查方向

遵循本指南，操控成功率可提升80%以上，彻底解决半途而废的问题。
