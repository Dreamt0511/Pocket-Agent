# 高速模式操作规范

## 核心理念：信任计算，减少人肉验证

**常规模式**（慢但稳）：
```
拿 UI 树 → 分析 → 点 A → 等 2s → 验证 → 点 B → 等 2s → 验证 → ...
```

**高速模式**（快但信任）：
```
拿 UI 树 → 一次性分析所有路径坐标 → 链式点击（0.3-0.5s间隔）→ 最后验证
```

## 一、速度瓶颈分析

| 环节 | 耗时 | 能否优化 |
|:---|:---:|::---|
| **UI 树获取** | ~50ms | ✅ 一次拿够，避免重复请求 |
| **坐标计算** | ~10ms | ✅ 内存计算，几乎免费 |
| **tap 执行** | ~6ms | ❌ NeuralBridge 硬件延迟 |
| **App 响应/页面加载** | 1-3s | ❌ 网络/渲染硬性等待，最长 2s，极端 3s |
| **验证（get_ui_tree）** | ~50ms | ✅ 一般操作直接验证无需等待，仅页面加载时 wait_for_idle 2s |
| **文本输入（粘贴）** | ~200ms | ✅ 比打字快 20 倍 |
| **Termux 浮窗处理** | ~2s | ✅ 在任务开始时一次性处理 |

**核心原则：App 加载等待无法避免，但人的决策等待和多余的验证可以消除。**

## 二、高速操作五原则

### 原则 1：一次扫描，多次复用

```bash
# ❌ 慢：每步都拿 UI 树
tap A → sleep 2 → get_ui_tree → analyze → tap B → sleep 2 → get_ui_tree → ...

# ✅ 快：一次拿够所有坐标
get_ui_tree → compute all targets → tap A → sleep 1 → tap B → sleep 1 → tap C → ...
```

在任务开始时获取一次完整的 UI 树（`filter="all"`），解析出所有感兴趣的元素的 bounds，然后连续操作。只有在页面发生重大变化（导航到新页面）时才重新获取。

### 原则 2：链式点击，压缩间隔

```bash
# ❌ 慢：每步间隔 2-3s
tap && sleep 3 && tap && sleep 3 && tap

# ✅ 快：间隔 0.3-0.5s，只在大页面跳转时等 2s
tap && sleep 0.3 && tap && sleep 0.3 && tap
```

- 同一页面内的连续操作：0.3-0.5s 间隔，无需等待
- 页面跳转（点完等新页面加载）：`android_wait_for_idle(timeout_ms=2000)`
- App 冷启动：`android_wait_for_idle(timeout_ms=3000)`（极端情况）

### 原则 3：剪贴板粘贴替代打字

```bash
# ✅ 快：剪贴板粘贴（~200ms）
set_clipboard("机械键盘")
press_key("paste")

# ❌ 慢：逐字输入（~3-5s）
input_text("机械键盘")
```

对任何超过 2 个字符的文本输入，一律用剪贴板粘贴。注意 paste 需要输入框已有焦点。

### 原则 4：只在关键节点验证

**必须验证的节点**：
- 页面跳转后（确认目标页面已加载）
- 支付/下单前（确认金额正确）
- 提交信息前（确认内容正确）

**跳过验证的节点**：
- 同一页面内的连续标签/分类切换
- 输入框焦点/点击动作
- 滚动操作

### 原则 5：Termux 浮窗前置处理

每次任务开始时第一个动作就是检查并关闭 Termux 浮窗（如果有），避免中途被挡：

```bash
get_ui_tree → 检查 app 是否为 com.termux.window → 是则点 exit_button → 继续
```

## 三、典型任务的快速流程

以"搜索商品→咨询客服→看评价→下单→到付款页通知"为例：

### 阶段 1：启动与搜索（~6s）

```
① 关 Termux（如有） + am start -p 启动 App（并行）         0.5s + 2s 等待
② get_ui_tree（一次性获取全部元素）                         0.1s
③ 计算搜索框坐标 + 点击                                     0.3s
④ set_clipboard + press_key paste                           0.3s
⑤ press_key enter（搜索）                                   1s
⑥ get_ui_tree（获取搜索结果）                               0.5s
                                                            合计：~5s
```

### 阶段 2：选商品与咨询客服（~7s）

```
⑦ 从搜索结果中计算目标商品坐标 + 点击                       0.3s + 2s 等待
⑧ get_ui_tree（获取商品详情页元素）                         0.5s
⑨ 计算"客服"按钮坐标 + 点击                                 0.3s + 2s 等待
⑩ get_ui_tree（获取聊天界面元素）                           0.5s
⑪ 找到输入框 → set_clipboard + paste + 发送                1s
⑫ get_ui_tree（确认消息已发送）                             0.5s
                                                            合计：~7s
```

### 阶段 3：看评价与下单（~9s）

```
⑬ 返回商品页 → 点"评价"标签                                 0.5s + 2s 等待
⑭ get_ui_tree（获取评价内容）                               0.5s
⑮ 文本分析有无差评                                          0.1s
⑯ 返回 → 点"立即购买"                                      0.5s + 2s 等待
⑰ get_ui_tree（确认到订单页面，核对金额）                   0.5s
⑱ 选规格颜色 → 点"确定" → 到付款页                          0.5s
⑲ get_ui_tree（确认付款页面）                               0.5s
⑳ termux-vibrate（震动通知用户）                            0.1s
                                                            合计：~9s
```

**全流程总时间：约 22s**（人类手动操作约 60-90s）

## 四、应用类型与速度分级

| 应用类型 | 代表 | UI 树 | 速度 | 策略 |
|:---|:---|:---:|:---:|:---|
| **标准原生** | 拼多多、淘宝、京东 | ✅ 完整 | 🚀 最快 | 链式点击 + 剪贴板输入 |
| **WebView 混合** | 部分工具类 App | ⚠️ 部分 | ⚡ 快 | 同标准，但输入用粘贴方案B |
| **自定义渲染** | 微信、小红书 | ❌ 空 | 🐢 慢 | 截图 + VLM 视觉分析 |
| **游戏/SurfaceView** | 游戏、视频播放器 | ❌ 空 | 🐢 极慢 | 仅坐标点击，需人工辅助 |

## 五、安全约束

### 禁止操作（必须硬编码阻止）
1. **禁止点击任何带"付款""支付""确认支付""输入密码"等字样的按钮**——除非任务明确要求
2. **禁止点击"直接成团""发起拼单""立即购买"等购买按钮**——除非经过用户确认
3. **禁止自动输入密码或支付信息**

### 强制验证节点
- 到达任何涉及金钱的页面时，**必须先 get_ui_tree 确认页面内容**，再执行下一步
- 如果不确定当前页面是否有支付风险，**停下来问用户**

### 失败处理
- 链式操作中某一步失败（如找不到目标元素）：尝试 1 次重扫 UI 树
- 重扫后仍失败：停止链式，报告具体失败的步骤
- 禁止无限制重试或猜测坐标

| 翻 50 条商品列表 | 30s | 45s | 15s |
